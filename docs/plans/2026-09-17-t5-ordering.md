# T5 — Ordering

Detail plan for the fifth template phase. Sits under
`docs/plans/2026-09-10-storefront-implementation-plan.md` §T5 and replaces its bullet list with
something buildable. T0–T4 are merged; this is the next phase and nothing in the tenant track
starts until the template track finishes.

**Exit:** full round trip — cart, submit, price in admin, accept, order exists.

**Status: items 1 and 2 built** — the accept claim and the placer, and quote lines that record
the price the customer was shown. Items 3-9 are planned.

Three things in this plan changed once item 1 met the code, and the sections below say so
inline: there is no `spQuote_Accept` (the claim went into `spOrder_ConvertFromQuote`, because
two procedures would be two guards that drift), `Quote` gained no `PoNumber` (the order carries
it; a quote that was never accepted has none), and `spOrder_GetByQuote` was needed so a
conversion can read back the order it created.

T5 is the phase the whole seam discussion in §2 of the implementation plan was about:
"Building Phase T5 as 'the quote flow' with no seam is the single most expensive assumption to
unwind." The seam exists — `IOrderingMode`, `OrderingModeProvider`, `RfqOrderingMode` — and so
far nothing has had to flow through it. This is where it earns its keep or turns out to be
decoration.

Unlike T4, this is not mostly finishing what exists. The pieces that exist are the *admin*
half: `dbo.Quote`, `dbo.QuoteLine`, `spQuote_*`, `spOrder_ConvertFromQuote`, and the portal
screens over them. The storefront half is a stub — `Basket.razor` renders "Basket lines land
with T5" and `Product.razor`'s add button is permanently `disabled`. And the admin half was
written for an admin typing numbers into a form; several of its assumptions do not survive a
customer submitting a basket, which is what §1 to §4 below are about.

---

## 1. The decision that comes first: where a basket lives

Every other piece of T5 depends on this one, so it is settled before anything is written.

The implementation plan says: "Server-side quote cart (persisted per contact; `localStorage`
only for anonymous visitors, merged on sign-in)." The first half is right. The second half is
the wrong shape for this storefront, and the reason is a constraint that postdates the July
design.

### Not `dbo.Quote` with a `Draft` status

The cheapest-looking option, and it does not work:

- `Quote.AccountId` is `NOT NULL` with a composite foreign key to `Account(Id, SiteId)`. An
  anonymous visitor has no account, so an anonymous basket cannot be a `Quote` row at all.
- `Quote.Reference` is assigned from `dbo.QuoteReferenceSequence` on insert. Every abandoned
  basket would burn a `QT-` number, so the references a customer sees would have gaps
  proportional to the store's bounce rate.
- `spQuote_GetAll` feeds `/admin/quotes` **and** `spActivity_GetRecent` feeds the dashboard. A
  draft would appear in both as a request nobody made, and suppressing it means a
  `Status <> 'Draft'` predicate in every query over the table, forever.

That last point is `dbo.Purchase` again. One table doing double duty, every query needing a
predicate to tell the halves apart, and the discipline holding only as long as everybody
remembers — and §6 below records the one procedure where it already did not hold.

### Decision: `dbo.Basket` and `dbo.BasketLine`, keyed by a token in a cookie

A separate pair of tables, site-scoped, with a nullable `ContactId`:

- **Signed in:** the basket is found by `ContactId`. Per contact rather than per account,
  because two buyers at one company assembling one shared list is a surprise, not a feature.
- **Anonymous:** the basket is found by an opaque `Token`, which arrives in an `HttpOnly`
  cookie. 256 bits of `RandomNumberGenerator` output, not a sequential id — the token *is* the
  authorisation to read that basket, so it has to be unguessable in the way a `Basket.Id` of
  `41` is not.
- **On sign-in:** one `UPDATE` sets `ContactId` on the token's basket. Merging two baskets is
  an `UPDATE` and a `DELETE` in one procedure, entirely server-side.

### Why not `localStorage`

`SMStore` is static SSR with no interactive render mode on any page, deliberately — the mobile
menu is a CSS-only disclosure specifically to avoid a Blazor circuit on every page. Under that
constraint a `localStorage` basket costs:

- JavaScript to read and write it, where there is currently none;
- either JavaScript to render it, or a round trip that posts the contents up before the page
  can show them;
- a handoff at sign-in, which means the browser posting a list of product ids and prices that
  the server then has to distrust and re-resolve anyway.

The cookie carries an opaque id, so none of that appears. It also fixes a problem the
`localStorage` design has and hides: **basket contents in client storage are client-editable.**
A basket holding prices in the browser is a basket where the price is a suggestion, and the
server must re-resolve every line on submit — at which point the client copy was never the
source of truth and only ever bought a render.

Cost of the cookie approach, stated plainly: an anonymous basket row per visitor who adds
something, including crawlers. `spBasket_PurgeAbandoned` and a retention window go in the plan
below rather than being discovered as table growth.

## 2. The second decision: what stops two accepts

`spOrder_ConvertFromQuote` today:

```sql
UPDATE dbo.Quote
SET [Status] = 'Accepted'
WHERE [Id] = @QuoteId;
```

No predicate on the current status. Two callers accepting the same quote produce **two orders
from one quote**, each with its own `SO-` reference and its own copy of every line. Nothing in
the schema prevents it: `Purchase.QuoteId` has a foreign key to `Quote(Id, SiteId)` but no
unique constraint.

That is reachable today by an admin double-clicking "Convert to order". T5 makes it ordinary,
because the customer gets an Accept button of their own and both paths land here.

### Decision: the status transition is the claim

Exactly T4's shape, which is why it is the second thing decided rather than found later:

```sql
UPDATE dbo.Quote
SET [Status] = 'Accepted'
WHERE [Id] = @QuoteId AND [SiteId] = @SiteId AND [Status] IN ('Requested', 'Priced');

IF @@ROWCOUNT = 0 THROW 50010, 'That quote is no longer awaiting acceptance.', 1;
```

The `UPDATE` moves to the top of the transaction and the `WHERE` and `SET` share one row lock,
so two callers arriving together cannot both come away with a rowcount of 1. Reading the status
first and converting if it looked right is the same code with a race in the gap, and the gap is
exactly where a customer's Accept and an admin's Convert meet.

It lives in `spOrder_ConvertFromQuote` rather than in a new `spQuote_Accept`, and both
Requested and Priced are allowed through. This procedure's job is to stop a double conversion,
not to decide who may convert when — an admin converting an unpriced quote is a deliberate act.
The customer's rules (priced, and not expired) live on the customer path in §5, where they can be
answered with a page rather than an error. Two procedures would have been two guards, and two
guards over one invariant drift.

Second guard, belt to that brace: `UQ_Purchase_QuoteId`, a unique index on `QuoteId` filtered to
`WHERE QuoteId IS NOT NULL`. Filtered because POS rows leave it NULL and SQL Server treats NULL
as one distinct value in a unique constraint — unfiltered, the second POS sale ever would fail.

**A rejected transition is not a failure.** Same conclusion as T4's refused claim: somebody else
decided it while the screen was open, which for an accept is the ordinary case rather than an
error. It answers 409 and the customer is shown the quote's real state.

## 3. What a quote line stores, and why the procedure must stop deriving it

`spQuoteLine_Insert` derives the net price:

```sql
DECLARE @NetPrice money = @ListPrice - (@ListPrice * @DiscountPct / 100.0);
```

Correct for the caller it was written for — an admin typing a list price and an integer
discount. Wrong for the storefront, in two ways that both end with a customer being charged a
number they were not shown:

- **`PriceResolver`'s effective discount is not an integer.** When the site's `MinMarginPct`
  floor binds, the net price is `cost × (1 + margin)` and the discount that produces it is
  whatever it happens to be — `EffectiveDiscountPct` is a `decimal` for that reason.
  `QuoteLine.DiscountPct` is an `INT`. Truncating it and re-deriving net gives a different
  price. (A *group* discount is integral: `CustomerGroup.Discount` is an `INT` column and
  `fnCatalog_VisibleProducts` takes `@DiscountPct int`. The floor is the only thing that
  makes an effective discount fractional today, and `Site.MinMarginPct` is `DECIMAL(5, 2)`.)
- **Even without the floor, the two arithmetics need not agree.** `PriceResolver` rounds to two
  places with `MidpointRounding.AwayFromZero`, on purpose, so two lines of one product round
  alike. The procedure does not round at all, and `money` carries four decimal places, so the
  stored net can hold fractions of a cent the displayed price never had. Measured, not
  supposed: 99.99 at 7% stored 92.9907 while the page showed 92.99 — a price nobody can
  pay, on the document the customer signs. This is the half that was already reachable,
  since no store has set `MinMarginPct`.

### Decision: the caller states the net price; the procedure derives only when it is not given

`@NetPrice money = NULL` is added to `spQuoteLine_Insert`, and the derivation runs only when the
parameter is absent. The admin path is untouched and the storefront path is explicit.

This is the existing parity rule extended by one step. CLAUDE.md already says SQL computes an
ordering key and `PriceResolver` computes the price a customer is shown. T5 adds: **and the
price a customer was shown is the price that gets stored.** `CatalogPriceParityTests` is what
keeps the first half honest; a test that a submitted basket line's `NetPrice` equals what
`CatalogPresenter` rendered keeps the second.

`QuoteLine.DiscountPct` widens to `DECIMAL(5, 2)` in the same change, with `QuoteLineModel` and
the portal's display following. Integers widen losslessly so no existing row or caller moves,
and the alternative is recording "-12%" against a price that a 12% discount does not produce.

## 4. The third decision: who placed the order

`Purchase.StaffId` is `NVARCHAR(128) NOT NULL` with `FK_Purchase_ToUser` into `dbo.User(UserId)`
— and `dbo.User` is staff. Its own table comment says so: "Distinct from `dbo.[User]`, which
holds staff — the people who run the store. A `Contact` is a customer's employee."

So a customer accepting their own quote has nothing to put in `StaffId`. Anything id-shaped
satisfies the C# compiler and fails `FK_Purchase_ToUser` with SQL error 547 **after** the caller
has been told it succeeded. That is the third time this exact shape has come up: T3's
`FK_Account_ApprovedBy` (found by the E2E suite, after four unit-test projects missed it), T4's
`DelistedProductHistoryTests` fixture, and now the accept path. It is settled before the accept
path is written rather than after.

### Decision: `PlacedByContactId`, and `StaffId` becomes nullable

- `Purchase.PlacedByContactId INT NULL`, foreign key to `Contact(Id)`.
- `Purchase.StaffId` becomes `NULL`-able. The foreign key still holds for every non-null value.
- `CK_Purchase_Placer`: a row carrying a `Reference` has exactly one of the two set. A POS sale
  has `StaffId` and no `Reference`, and is unaffected.

A synthetic `dbo.User` row per store — "storefront" — was considered and rejected. It puts a
fictional employee in `spPurchase_PurchaseReport`'s output and in the "Prepared by" line on
every document, and the whole point of recording who placed an order is that the answer is true.

**One procedure changes behaviour because of this, silently, and it is worth naming.**
`spPurchase_PurchaseReport` INNER JOINs `dbo.User` on `StaffId` and — alone among the procedures
over this table — carries **no** `Reference` predicate in either direction. It therefore already
returns portal orders, attributed to whichever admin converted them. Once `StaffId` can be NULL,
a customer-accepted order drops out of that report through the inner join. For a POS report that
is the right answer arrived at by accident, so T5 makes it deliberate: the procedure gets
`WHERE s.Reference IS NULL`, which is the other half of a discipline CLAUDE.md currently
describes as holding on the `spOrder_*` side only.

## 5. What the customer may read, and what an accept refuses

### A reference is not an authorisation

`spQuote_GetByReference` and `spOrder_GetByReference` scope by site and nothing else. That is
right for an admin, who may see every quote in their store. It is **not** enough for a customer:
references come from a sequence and read `QT-0041`, `SO-0012`, so site-only scoping means any
signed-in customer can read any other customer's quote — their lines, their prices, their
discount — by changing a digit.

So the customer-facing reads are their own procedures with the account in the predicate, not the
admin ones with a different caller:

- `spQuote_GetByAccount`, `spOrder_GetByAccount` — the list pages.
- `spQuote_GetForAccount`, `spOrder_GetForAccount` — one document, by reference, `@AccountId`
  **and** `@SiteId` both in the `WHERE`.

Both answer empty for "not yours" exactly as they do for "not here", for the reason
`AccountDocumentController` already answers 404 rather than 403: with sequential ids, a
distinguishable refusal confirms the row exists.

The account comes from `ICustomerContext`, which resolves it from the session per request. Never
from a route parameter or a form field — the same rule that is why there is no `/account/{id}`.

### Expiry blocks, delisting warns, staleness never arrives

T4 deferred one decision to T5: whether a quote carrying a delisted line should be acceptable,
or re-quoted first. `DelistedProductHistoryTests` records the current behaviour so the choice is
made rather than discovered. Three cases, three different answers:

- **Expired blocks.** `Quote.ExpiresDate` is a statement the store already made in writing. The
  accept is refused and the customer is offered a re-quote — which is one button, because the
  basket tables in §1 make re-quoting a copy rather than a re-entry.
- **Delisted warns, and still accepts.** The price was quoted; withdrawing it at the moment of
  acceptance pushes a supply problem the store owns onto the customer. The line is flagged on
  the acceptance page and on the order, and sales sees it on the order rather than learning
  about it from a complaint. Blocking would leave the customer stuck behind a button that
  cannot succeed until somebody notices.
- **Staleness never reaches a quote line at all.** Already the rule in CLAUDE.md: hiding stock
  from the shop window is not withdrawing a price already quoted. The accept path must not
  acquire a staleness predicate, and `spQuoteLine_GetByQuote` and `spOrder_ConvertFromQuote`
  must not acquire one either. `DelistedProductHistoryTests` covers the delisted half; the stale
  half gets its own case.

Worth stating because it is the obvious next idea and it is wrong: **stock is not checked at
acceptance.** T4 recorded that on-demand stock confirmation needs an API the distributor feed
does not have. A quantity check against `Product.QuantityInStock` would be a check against
whatever the last file said, presented to the customer as a live answer.

## 6. Schema

**New tables:**

- `dbo.Basket` — `Id`, `SiteId`, `ContactId NULL`, `Token`, `CreatedUtc`, `UpdatedUtc`.
  `UQ_Basket_Token`; `UQ_Basket_Contact` filtered to `WHERE ContactId IS NOT NULL`, so one
  signed-in contact cannot accumulate baskets. `FK_Basket_ToSite`, `FK_Basket_ToContact`.
- `dbo.BasketLine` — `Id`, `BasketId`, `ProductId`, `Quantity`, `AddedUtc`.
  `UQ_BasketLine_Product` on `(BasketId, ProductId)`: adding the same product twice raises the
  quantity rather than making a second line. **No price columns** — a basket line names a
  product and a quantity, and the price is resolved at submit. A price stored here would be a
  price the customer could hold on to while the catalog moved.

**Altered tables:**

- `Quote` — `CK_Quote_Status` over the four documented values. The column has carried them
  in a comment since it was written; the accept path now gates on them, so they are enforced.
  `CustomerNote NVARCHAR(1000) NULL` lands with submit (item 5) and a rejection reason with
  reject (item 6).

  **No `PoNumber` and no `AcceptedUtc` here**, both dropped while building item 1. The order
  carries the PO — a quote that was never accepted has none, and holding it in two places is
  holding a value that can disagree with itself. `Purchase.PurchaseDate` already records the
  instant the acceptance happened.
- `QuoteLine` — `DiscountPct` widens to `DECIMAL(5, 2)` (§3).
- `Purchase` — `PlacedByContactId INT NULL`, `PoNumber NVARCHAR(50) NULL`, `StaffId` becomes
  nullable, `CK_Purchase_Placer`, `UQ_Purchase_QuoteId` filtered to `WHERE QuoteId IS NOT NULL`
  (§2, §4).

**New procedures:**

- `spBasket_Get`, `spBasket_EnsureForToken`, `spBasket_AddLine`, `spBasket_SetQuantity`,
  `spBasket_RemoveLine`, `spBasket_Claim` (the sign-in merge), `spBasket_PurgeAbandoned`.
- `spQuote_SubmitRequest` — the basket's lines and a resolved price per line arrive as a table
  type, the quote and its lines are written in one transaction, the basket is emptied.
- `spQuote_Reject` — with the customer's reason, which is quoted back to sales.
- `spQuoteLine_Update` — admin re-pricing. Missing today: `QuoteController` can add and delete a
  line but not change one, so "price in admin" in the exit criterion has nothing behind it and
  the portal's "Save draft" button is a `Toast.Show` over no write.
- `spQuote_GetByAccount`, `spQuote_GetForAccount`, `spOrder_GetByAccount`,
  `spOrder_GetForAccount` (§5).
- `spOrder_GetByQuote` — not foreseen, and needed by item 1. `OrderData` read a conversion
  back as "the store's newest order", which under two conversions at once is the other
  caller's. `UQ_Purchase_QuoteId` makes one order per quote a database fact, so the quote is an
  exact key.

**New table type:** `dbo.QuoteRequestLine` — `ProductId`, `Quantity`, `ListPrice`,
`DiscountPct`, `NetPrice`. Same reasoning as `DistributorFeedItem`: a basket is small, but the
submit has to be one transaction, and a per-line round trip inside one is a transaction held
open across the network.

**Altered procedures:** `spQuoteLine_Insert` (`@NetPrice` optional, §3);
`spOrder_ConvertFromQuote` (the claim, the placer, the PO number);
`spPurchase_PurchaseReport` (`Reference IS NULL`, §4); `spQuote_GetByReference` and
`spOrder_GetByReference` project the new columns.

**Also needed by item 1, and not foreseen:** `UQ_Contact_IdAccount` on
`Contact(Id, AccountId)`, because `FK_Purchase_ToContact` is composite over the account and a
composite foreign key needs a matching unique key to point at — the same dependency
`UQ_DistributorFeed_IdSite` had in T4. And `QuoteStatus` in the library, naming the four states
in one place so the API can refuse a fifth before `CK_Quote_Status` turns it into a 500.

## 7. Work items, in order

Each is one commit, and the order is the dependency order — the decisions above are items 1
and 2 because everything after them assumes the answers.

**1. The accept claim and the placer. Built.** `spOrder_ConvertFromQuote` gained the
status-transition claim, `UQ_Purchase_QuoteId`, `PlacedByContactId`, a nullable `StaffId`,
`CK_Purchase_Placer`, `CK_Quote_Status`, `UQ_Contact_IdAccount`, `spOrder_GetByQuote`, and
`spPurchase_PurchaseReport`'s missing predicate. No storefront UI. This is the T4 pattern:
settle concurrency and the foreign key before writing anything that depends on either. The
admin Convert button moved onto the same procedure in the same commit, so both paths share one
guard from the start rather than converging later, and it now reports three outcomes instead of
two.

  One trap found here, recorded in `QuoteAcceptanceTests`: **T-SQL has no nested transactions,
  so the procedure's `ROLLBACK` unwinds a test's rollback scope as well.** A test that provokes
  the procedure's `CATCH` has to do it last and touch nothing afterwards. The validation
  failures are raised before the transaction opens and are safe anywhere.

**2. Quote lines record what the customer was shown. Built.** `@NetPrice` optional on
`spQuoteLine_Insert`, `DiscountPct` widened to `DECIMAL(5, 2)`, `QuoteLineModel`, the API
contract and the portal display following it, and `QuoteLinePriceTests` pinning the derived
path to `PriceResolver` over a matrix the way `CatalogPriceParityTests` pins the sort key.

  The rounding half turned out to be the concrete one: the old expression did no rounding at
  all, so 99.99 at 7% stored 92.9907. `money` carries four decimal places, and that number
  reached the quote document. The floor half is real too but needs a store to have set
  `MinMarginPct`, and none has.

**3. The basket, server-side.** The two tables, the six procedures, `IBasketData`, and
`BasketService` in `SMStore/Ordering/` — token minting, the cookie, and the sign-in merge hook
in `CustomerAuthEndpoints`. No pages yet; tested through the service.

**4. The basket, on the storefront.** `Basket.razor` for real, `Product.razor`'s add button
wired, a line-count badge in `StoreNavigation`. Form posts to endpoints under
`SMStore/Ordering/`, with `<AntiforgeryToken />`, exactly as `Login.razor` and
`ForgotPassword.razor` do — no interactive render mode is introduced, and if one ever is it
should be a deliberate decision about one island rather than a side effect of a quantity
stepper. Everything user-facing reads its words from `IOrderingMode`: this is the commit where
the seam either works or is revealed as decoration, so no string in these pages says "quote".

**5. Submit.** `spQuote_SubmitRequest`, the table type, the submit endpoint, rate limiting on
it, and the acknowledgement page. Prices are re-resolved server-side at submit from
`CatalogPresenter` — never from the posted form, which is a client's opinion about what things
cost. The quote lands `Requested` in the existing admin queue, which needs no change.

**6. The customer's quotes and orders.** The four account-scoped procedures, `/account/quotes`,
`/account/quotes/{reference}`, `/account/orders`, `/account/orders/{reference}`, accept and
reject with the PO number, and the two "Lands with T5" panels on `Account.razor` replaced with
what they promised.

**7. Admin re-pricing.** `spQuoteLine_Update`, the controller action, and `QuoteDetail.razor`'s
"Save draft" turned into a write. Also "Send to customer", which is the `Requested → Priced`
transition the customer's accept gate depends on — today it is a toast.

**8. Documents.** See §8; the decision comes before the commit.

**9. End to end.** A Playwright journey covering the whole exit criterion in one pass: add,
submit, price in admin, accept, order exists. T3's evidence is the argument for spending this
here — the E2E suite found a foreign-key bug that four unit-test projects could not, and this
phase touches three foreign keys and a nullable column.

## 8. Documents: an open decision

"Quote and order PDF generation, templated per site" needs a renderer, and the candidates carry
different costs.

- **QuestPDF** is the strongest .NET option and its Community licence is free only below a
  revenue threshold. This repository already pinned FluentAssertions to 7.2.2 for exactly that
  reason — "8.0 moved to a licence that is not free for commercial use" — so taking a
  revenue-conditional dependency without asking would contradict a decision already recorded.
- **A print-styled Razor page** — `/account/quotes/{reference}/print`, `@media print` in the
  site's theme, printed to PDF by the browser. No dependency, no licence question, per-site
  templating for free because it is already themed. It cannot produce a file to attach to an
  email, which T6 wants.
- **Headless Chromium** via the Playwright already in the solution. Real PDFs, no new licence,
  and a browser in the deployment — which is T7's problem and a large one.

**Recommendation:** build the document as a Razor component with print styles (item 8), because
that is the part that is the same under all three, and settle the renderer with T6 when the
outbox makes an attachable file actually necessary. **This needs a decision before item 8 is
built**, and it is the one open question in this plan.

## 9. Not in T5

- **Tax.** `spOrder_ConvertFromQuote` writes `VAT = 0` and T6 owns the rule engine. The
  portal's quote screen shows "VAT (23%)" as a hardcoded string; T5 does not fix it and does
  not copy it into the storefront. A quote document says tax is calculated on the order.
- **Payment.** `Purchase.Status` starts at `Awaiting payment` and nothing moves it. No card
  flow, and the credit-terms check at acceptance is T6's.
- **Email.** Five state changes in T5 deserve mail — quote received, quote priced, quote
  accepted, order confirmed, quote expiring. The call sites are written against `IEmailSender`
  the way T3's were, so T6 fills them rather than finding them.
- **`DirectCheckout`.** The mode stays unbuilt. T5's job is to prove the seam holds for one
  implementation, which means no page outside `SMStore/Ordering/` acquiring the word "quote".
- **Expiring quotes.** `ExpiresDate` gates the accept (§5) and nothing sweeps the table. A
  `Requested` quote nobody prices stays that way.
- **Editing a submitted quote.** A customer who wants a different quantity submits again.
- **Order cancellation by the customer.** Status changes stay with the admin.

## 10. Risks

- **The seam is unproven and this is the phase that tests it.** `IOrderingMode` has five
  strings and two booleans, all chosen before anything consumed them. If the basket pages need
  something it does not expose, add it to the interface rather than branching on
  `Site.OrderMode` — that branch is the assumption the seam exists to prevent, and it will look
  reasonable at the call site.
- **Nullable `StaffId` touches the desktop POS's table.** The column is written by
  `spPurchase_Insert` and read by `spPurchase_LookUp` and `spPurchase_PurchaseReport`. The
  report is handled in item 1; the other two pass it as a parameter and are unaffected. `SMDesktopUI`
  must be built and its UI tests run before item 1 merges — they need an interactive desktop, so
  this is a manual step, and it is the one place in T5 where the legacy app can break silently.
- **Anonymous basket rows grow without a sweep.** `spBasket_PurgeAbandoned` is in item 3, and
  nothing calls it on a schedule. `DistributorFeedSyncBackgroundService` is the obvious host and
  is off by default, so a store with the scheduler disabled never purges. Decide the caller in
  item 3 rather than leaving the procedure as something that exists and never runs.
- **`Site` still has no admin screen.** T4 recorded it and T5 adds nothing to it, but the list
  of things a tenant cannot configure without database access grows: `OrderMode` is now
  load-bearing, and a store whose `OrderMode` names an unbuilt mode fails every page with
  `OrderingModeProvider`'s exception rather than degrading.
- **Admin reads are still not site-scoped.** Unchanged by T5 and still a prerequisite for a
  second tenant. Nothing in this phase makes it worse; the customer-facing reads in §5 are
  account-scoped from the start specifically so they do not have to be retrofitted the way the
  admin ones will.
- **A rejected `Requested` quote has no route back.** The customer can reject a `Priced` quote.
  A quote they submitted and now regret has no cancel, and item 6 should not grow one without
  deciding what sales sees.
